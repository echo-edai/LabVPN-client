# 睡眠、网络变化与端口恢复

## 原有缺陷

- 自动恢复仅调用回环控制 API。核心存活而物理出口、DNS 或 TUN 通路异常时，控制 API 成功不能证明网络可用。
- 端口选择把普通用户的任何 `bind` 失败都当成“其他程序占用”，没有监听或进程归属证据。TUN 核心实际由管理员 helper 运行，两者绑定权限可能不同；刚关闭的连接也不等于仍有活跃监听。
- 混合代理与控制端口独立选择，未预留同次连接已经选中的端口；邻近候选可能撞在一起。候选耗尽后仍返回原端口，推迟了错误暴露。

## 修复行为

1. 确认自己的旧 helper 核心停止后，再选择新会话端口。TUN 模式探测活跃 TCP 监听，实际绑定由 helper 核心完成；普通模式使用地址复用后的绑定与监听探测。启动探测不能消除其他进程同时抢端口的竞争，核心启动结果仍是最终依据。
2. 保留同次连接选中的端口，防止混合代理与控制端口重复。候选耗尽立即报错。提示包含失败原因，不在未确认归属时归因第三方软件。
3. 恢复监控在内存记录物理地址指纹。指纹变化或轮询墙上时间间隔超过 45 秒，进入额外检查窗口；该阈值也可能捕获进程暂停，不等于原生睡眠事件。
4. 物理地址连续两轮稳定后才允许恢复；无物理地址时等待。两轮之间是正常 15 秒轮询间隔，这不是完整的 DHCP 或网关就绪证明。
5. 控制 API 存活时，检查系统路由与混合代理两条 HTTPS 通路；任一成功就保留当前核心。两条通路连续两轮都失败，才重建核心。请求不带账号或本机诊断信息，站点与现有“一键检查网络”一致。
6. 保留连接操作锁、手动断开意图与十分钟最多三次的恢复预算。旧核心停止未确认时不启动新核心。

## 验证及限制

- 回归覆盖活跃监听、端口释放后复用、同次连接端口去重、候选耗尽、暂停后接口不变、网络离线、地址变化、稳定窗口及连续失败阈值。
- 本地 Rust 测试合计 131 项通过（core 84、desktop 33、helper 14），需要真实日志输入或修改系统代理的 2 项测试保持忽略。执行 `cargo test --workspace` 后，新增端口用例再次执行 `cargo test -p labvpn-desktop`；Clippy `--workspace --all-targets -- -D warnings`、前端 `npm run typecheck` 和 `npm run build:web` 通过。运行日志留在忽略的 `work/audit/`，不随源码发布。
- 自动测试不执行系统睡眠、TUN 重建或系统代理修改。实际合盖唤醒、Wi-Fi 漫游、DHCP 变化、跨权限连接回收及长时间 SSH 会话需要原生回归。
- 短于 45 秒且未被轮询观察到物理地址变化的睡眠，不保证进入额外检查窗口；后续可接入平台原生睡眠与网络路径通知。
- 重建核心会中断它承载的连接。此策略尽量避免健康连接被误重启，不能让已经失效的 SSH 会话无损恢复。

## 回滚

本次没有更改配置格式、分流规则或 helper 协议。若原生回归发现误恢复，回退本次源码提交并重新构建桌面程序即可；安装包替换和实际合盖测试需单独记录结果。
